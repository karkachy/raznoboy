# Как показать «Разнобой» на защите

Сервер работает на http://localhost:5198, сайт открывается на [http://localhost:5173](http://localhost:5173/). Запуск в двух терминалах: `npm start` в папке `Server` и `npm run dev` в папке `client`. В VS Code нажми **Ctrl+P**, введи путь из памятки, при необходимости добавь `:номер_строки` и нажми Enter.

## Короткий рассказ

«Это музыкальная афиша. Интерфейс написан на React и TypeScript. React Router связывает адрес страницы с компонентом. Библиотека Radix UI отвечает за диалоговые окна. Клиент работает на порту 5173 и получает данные по HTTP от сервера на порту 5198. Сервер написан на Node.js и Express, а каталог, аккаунты, голоса и билеты хранятся в SQLite».

## Если попросят показать архитектуру

| «Где маршруты клиента?» | [client/src/routes/AppRoutes.tsx](client/src/routes/AppRoutes.tsx) | В `AppRoutes` каждый `Route` связывает адрес с React-компонентом. Шаблоны адресов лежат рядом в `paths.ts`. Например, `/events/machine` открывает карточку, а `/events/machine/checkout` — покупку. |
| «Где страницы и компоненты?» | [ConcertPage.tsx](client/src/pages/ConcertPage.tsx) | Страница извлекает `eventId` из адреса через `useParams()`. В её JSX видны компоненты обложки, рейтинга и окна. Общий [PageDialog](client/src/components/PageDialog.tsx) собран из компонентов Radix UI. |
| «Где React Context?» | [SessionContext.tsx](client/src/auth/SessionContext.tsx) | `SessionProvider` хранит ответ сервера в состоянии React. Шапка, профиль и карточка получают его через `useSession()`. После F5 провайдер снова вызывает `api.session()`. |
| «Как фронт и бэкенд связаны?» | [client/src/api.ts](client/src/api.ts) | В `API_URL` записан адрес сервера `http://localhost:5198/api`. Методы `api.events`, `api.login`, `api.buy` вызывают общую функцию `request`. Она отправляет `fetch` на этот адрес, передаёт cookie (`credentials: 'include'`) и разбирает ответ. |
| «Почему порты разные и как они общаются?» | [Server/middleware/cors.js](Server/middleware/cors.js), [client/vite.config.ts](client/vite.config.ts) | Клиент (Vite) работает на порту 5173, сервер (Express) на 5198. Это два отдельных приложения: клиент отдаёт страницу, сервер — только данные в JSON. Для браузера другой порт означает другой источник, поэтому сервер в `cors.js` явно разрешает запросы с `http://localhost:5173`. Перед PUT, PATCH, DELETE браузер сначала шлёт проверочный запрос `OPTIONS`, сервер отвечает 204 с разрешёнными методами. |
| «Почему package.json в каждой папке?» | [Server/package.json](Server/package.json), [client/package.json](client/package.json) | У сервера и клиента свои зависимости и команды: сервер — `express`, `cookie-parser`, `npm start`; клиент — `react`, `vite`, `npm run dev`. Поэтому в каждой папке свой `package.json`, `package-lock.json` и `node_modules`. В корне проекта общих пакетов нет. |
| «Где маршруты сервера?» | [Server/app.js](Server/app.js) → [Server/routes/tickets.js](Server/routes/tickets.js) | `app.use('/api/tickets', ticketRoutes)` задаёт префикс; в отдельном файле `ticketRoutes.post('/:eventId', requireUser, …)` описывает покупку. Вместе получается `POST /api/tickets/machine`. |
| «Где проверяется пользователь?» | [Server/middleware/session.js](Server/middleware/session.js) | `readSession` читает cookie, находит сессию, проверяет срок и заполняет `req.user`. `requireUser` пропускает вошедшего зрителя к обработчику покупки или оценки. |
| «Где база данных?» | [Server/db/connection.js](Server/db/connection.js), [schema.sql](Server/db/schema.sql) | Всё про базу лежит в папке `Server/db/`: **сам файл базы `afisha.db`**, описание таблиц `schema.sql`, начальные данные `seeds/`, SQL-запросы в `.js` файлах. `EventDetails` хранит данные афиш, `Tickets` — билеты, `Votes` — голоса пользователей, `SeedVotes` — исходные оценки. Показать содержимое: в папке `Server` выполнить `npm run db` (все таблицы и число строк) или `npm run db -- Tickets` (строки одной таблицы). |

## Покупка билета — от щелчка до записи в профиле

1. В [ConcertPage.tsx](client/src/pages/ConcertPage.tsx) найди **Купить билет**. Ссылка ведёт на страницу оформления выбранного концерта. Если гость ещё не вошёл, компонент `Protected` направляет его на `/login`. В параметре `next` остаётся адрес покупки, и форма входа возвращает зрителя к тому же концерту.
2. В **`client/src/pages/CheckoutPage.tsx:28`** начинается обработчик `confirm`. Выше видно `useState(() => crypto.randomUUID())`: идентификатор создаётся один раз для открытого оформления. Нажатие «Подтвердить покупку» блокирует кнопку и вызывает `api.buy(event.id, requestId)` на строке **33**.
3. В [api.ts](client/src/api.ts) найди **buy:**. На примере Machine Girl в адресе запроса находится `machine`, а в теле — `requestId`. В [routes/tickets.js](Server/routes/tickets.js) сервер проверяет вход и дату, затем вызывает `issueTicket(event, req.user.id, requestId)`.
4. В [db/viewer.js](Server/db/viewer.js) найди **INSERT INTO Tickets**. Билет связывается с аккаунтом. Повторная отправка одного оформления использует тот же ключ; ограничение уникальности защищает от второй записи. Отдельная новая покупка того же концерта получает другой ключ.
5. Вернись в **`client/src/pages/CheckoutPage.tsx:35`**. Клиент находит выданный билет в ответе, обновляет контекст и переходит на `/profile`. В **`client/src/pages/ProfilePage.tsx:44`** выражение `session.tickets.map` выводит все билеты этого пользователя. Видимый номер `RZ-…` строится из номера записи в БД.

**Что показать в браузере.** Открой [Machine Girl](http://localhost:5173/events/machine), выбери «Купить билет», при необходимости войди и подтверди оформление. На странице профиля видны номер, концерт, дата и площадка. При F5 сервер снова отдаёт список по cookie. В **F12 → Network → Fetch/XHR** у запроса покупки видны метод, адрес, Payload и Response. Оформление демонстрационное, без оплаты.

## Редактирование и удаление

| Действие | Где искать | Что объяснить |
|---|---|---|
| Изменить имя | [ProfilePage → NameEditor](client/src/pages/ProfilePage.tsx) → [routes/auth.js](Server/routes/auth.js) | Форма сначала проверяет имя на клиенте: пустое не отправляется, поле получает `aria-invalid`. Затем `api.rename` отправляет `PATCH /api/account`. Сервер повторяет проверку (1–30 символов) и выполняет `UPDATE Accounts`. Ответ обновляет контекст, и новое имя сразу видно в шапке. |
| Вернуть билет | [ProfilePage → TicketRow](client/src/pages/ProfilePage.tsx) → [routes/tickets.js](Server/routes/tickets.js) | Кнопка «Вернуть билет» сначала спрашивает подтверждение. `DELETE /api/tickets/:number` удаляет только билет текущего аккаунта (чужой — 404) и только до даты концерта (прошедший — 409). Во время запроса кнопка заблокирована. |
| Удалить оценку | [RatingPanel](client/src/components/RatingPanel.tsx) → [routes/ratings.js](Server/routes/ratings.js) | `DELETE /api/ratings/:eventId` удаляет голос из `Votes`. Средний балл снова считается по десяти исходным голосам. |
| Обработка ошибок и коды ответов | [routes/tickets.js](Server/routes/tickets.js), [app.js](Server/app.js), [api.ts](client/src/api.ts) | Каждый обработчик маршрута обёрнут в `try/catch`: ошибки проверки возвращают 400, 401, 404 или 409 с текстом, а непредвиденный сбой уходит через `next(err)` в общий обработчик в `app.js`, который отвечает 500 и пишет ERROR в лог. В терминале сервера каждый запрос выводится с кодом: 2xx зелёным, 4xx жёлтым, 5xx красным. На клиенте `request()` тоже использует `try/catch`: нет сети — «Нет связи с сервером», ответ не JSON — сообщение с кодом ответа. |
| Лог запросов | [middleware/logger.js](Server/middleware/logger.js) | Для каждого запроса к API пишется строка: время, метод, адрес, код ответа, длительность и ID пользователя. Ошибки 500 пишутся со стеком. Файл — `Server/logs/requests.log`. |

Тесты запускаются командой `npm test` в папке `Server` и в папке `client`. Серверные — [Server/tests/api.test.js](Server/tests/api.test.js), клиентские — [client/src/tests/flows.test.tsx](client/src/tests/flows.test.tsx) (проверяют число вызовов и параметры запросов, успешные и ошибочные ответы).
